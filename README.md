# PUB — Personal Utility Builder

Android host for small, locally stored JavaScript apps. Version 0.7.0 adds background building, completion notifications and durable build drafts to the launcher, ChatGPT builder, automatic visual repair and native hardware capabilities. A new install starts with one sample app, Tip Calculator.

## Use

1. PUB opens to **Your apps**, with an icon for each locally saved app. No project starts automatically. Long-press any app tile for **Edit app**, **Redesign icon**, **Use style guide** (on by default) or **Delete app**. **Redesign icon** designs a new pixel-art icon with the same icon step builds use and shows it next to the current one. It sends only the app's name, description and saved research summary, uses one or two plan requests, and changes nothing until you tap **Use new icon**. A new install starts with one sample app, **Tip Calculator**, copied into Your apps on first launch as an ordinary saved app: open, edit or delete it like any other. Deleting it is permanent (it is not added again), and upgrades and installs that already have apps don't get it.
2. Tap an icon to open its full-screen interface. The pinned **✕** (Close) button or Android Back stops its hardware sessions, shuts down its runtime and returns to the launcher.
3. Use **Settings** in the top-right for your ChatGPT connection, model preference, Style guide, global/per-app Access, and deleting saved apps. Changing a permission does not run that app. **Settings → Style → Edit style guide** sets one look for PUB and every app (light, dark or matching the phone; main, second and third colour; corners; font) with a live sample; changes apply at once, also to saved apps. Any app can be set not to follow it (long-press it, or the list on the same screen) and then uses PUB's default style. See `docs/style-guide.md`.
4. In Settings, **Continue with ChatGPT**, complete browser consent and return to PUB. Automatic model selection prefers the newest Astra returned by your account; if none is available it uses the first catalog model. An explicit model choice is saved, and Automatic restores the default.
5. Tap **New app**. The builder has three steps, shown as a rail at the top: **Describe**, **Review** and **Publish**. In Describe, type your instructions or use **Speak your idea**. Dictation appends editable text and never generates automatically. Android's speech service may process audio online even though PUB requests offline recognition when available. PUB receives text, not a recording. The global microphone block also disables dictation.
6. Tap **Build app**. PUB researches similar apps and best practices for your idea, plans its screens, then builds, tests the app's behavior and checks its first screen; the Describe step shows these phases as they complete. You can switch apps or turn off the screen meanwhile. Tap the completion notification (or **View build result** on the launcher) to return to the **Review** step: the draft with its checks, visual check and requested access, **Try it** to use it, and **Adjust** to change it; the research (with its sources), screen plan, checks and visual review are under **How it was built**. Then **Continue** to **Publish**, which says what saving does, and **Add to Your apps**: PUB saves the draft and opens it. **Save locally** in a preview saves it too. Closing an unsaved preview returns to the builder and discards its temporary app data; the generated draft remains available to try again.
   To adjust the draft, type or say what should change under **Request changes** in Review, or tap **Request changes** while trying it, then **Apply changes**. Each change builds on the current draft, the box clears for the next one, and **What you asked for** lists the idea and every change behind the draft. See "Follow-up changes" below.
7. Saved apps run locally and retain their private state. Delete from Settings (or the launcher) removes the package, state, files, photos, saved research and checks, permission override and style setting. Files and folders you picked for the app elsewhere on the phone are never deleted; only the app's access to them ends.
8. Tap **Edit** next to ✕ in an open app, or long-press a saved app and choose **Edit app**, to change it. Saving keeps the app's original request, research brief and behavior checks on the phone, so an edit builds on them: research updates the complete brief for the changed app, the builder keeps the checks that still apply and adds checks for the change, and the visual review judges the result against the full updated brief. The builder notes "Uses this app's saved research and N behavior checks" when an edit has them; apps saved before this version start without them until their next saved edit. Prompt history records how each request was researched and how many behavior checks passed.
No API key is used. ChatGPT authorization/plan eligibility and available models are controlled by OpenAI. One connected account is supported; disconnect before switching accounts. Cancel stops the current sign-in or generation. Build drafts are kept privately on the phone until you save or discard them; restarting Android/PUB during sign-in requires a fresh attempt.

## Data and boundaries

- Generation sends the user's app description, phone manufacturer/model, Android version, API level, screen dimensions, font scale, locale, light or dark theme, the app's style (style guide colours, corners and font; no text), hardware availability and PUB's supported runtime capabilities to OpenAI. Edits also send the current app package (code and asset definitions, no image pixels) and, when the app has a saved spec, its original request and behavior checks. Settings → Help & guide includes the exact phone context. It does not automatically include unique hardware identifiers, GPS coordinates, recordings, photos, saved app data or files, Bluetooth device names or credentials. Text the user puts in the description is sent when generating.
- Before building (new apps and edits), PUB sends a separate research request asking ChatGPT to research comparable apps, expected features, common complaints, domain rules and Android design guidance. It contains only the app description and, for edits, the existing app's name and description and its saved research brief (if any): no phone context, hardware details, app code, saved data or photos. When the ChatGPT connection allows it, the model uses web search; searches are performed by OpenAI's hosted web search, not by PUB or the phone's browser. The builder shows the result with its sources as links that open in the browser. Without web search, research uses the model's knowledge and is labelled that way; if research fails, the build continues from the description alone. See `docs/research.md`.
- After research, a separate UI planning request plans every screen of the app (navigation, first view, element order, states, interactions, wording, accessibility) within PUB's components and the phone's measured screen space, from the request, the research brief and PUB's component catalog. The builder implements the plan, repairs and the visual review judge against it, and it is saved with the draft and the app's spec so edits update it instead of starting over. A failed planning step never stops the build. See `docs/ui-planning.md`.
- Verification is automatic but bounded. The builder also writes behavior checks (based on the research brief's acceptance checks); PUB runs each one locally in a fresh isolated runtime with empty storage and no hardware, answering file requests from an empty in-memory folder and discarding all other effects, and automatically repairs failures. The visual review then checks the initial screenshot against the request and the research brief. Visual and behavior repairs share a limit of two per build. The checks are written by the same model as the app and cannot test hardware, permissions, saved data or timing, so preview and test the app yourself before saving. No extra data leaves the phone for the checks; repairs send the failing checks with the usual repair request. See `docs/behavior-checks.md`.
- Per-app specs: when an app is saved, PUB stores its original request, the build's research brief (with source links) and its behavior checks in a private file for that app (`files/app-specs/<app id>.json`). Specs stay on the phone, are deleted with the app, never contain the app's saved data, photos, phone context or credentials, and are sent to ChatGPT only as part of an edit request for that app (the brief to research; the original request and checks to the builder). A spec that cannot be read is ignored and left untouched; the next saved build replaces it. Prompt history keeps a short research summary and behavior-check result per request.
- The host has INTERNET permission for ChatGPT. Generated JavaScript still runs under a separate Android isolated UID with **no internet permission**, Java/Android bridge, DOM, or filesystem access; an app's private files are reached only through host-validated `files.request` effects, and files the user picks on the phone only through the `files` hardware capability, by opaque handles.
- App screens are built from PUB's native components, start-aligned like any Material screen. Buttons have four emphasis levels (`primary`, `secondary`, `text`, `danger`); `card` groups related content and can be tapped as a whole; `row` puts short texts or small buttons side by side; `item` is a compact list row with title, supporting and trailing text that can be tapped, checked or selected. Apps get a `resume` event when they come back on screen. Text is a label (up to 512 characters) or a `paragraph` for reading (up to 4,000). Inputs are single-line (up to 2,000 characters) or `multiline` for notes and other long text (several visible lines, up to 8,000), can ask for a number, decimal, phone or email `keyboard`, and can offer `voice` dictation: a microphone in the field opens the phone's speech service and adds the recognized text as if typed. The app only receives text, so dictation needs no capability or permission; the microphone block in Settings → Access turns it off.
- Supported hardware: camera still photos, foreground location, available standard sensors, BLE GATT and paired RFCOMM, headphone/audio routing, short tones/offline speech, haptics, torch, battery, read-only NFC NDEF, chosen USB bulk endpoints and infrared where physically available. `microphone.pitch` still sends only pitch/confidence/level. See `docs/hardware-runtime.md` for scope and limitations.
- Settings → Hardware inventory lists Android-exposed cameras, sensors, features, displays and accessory metadata, with detected-only hardware distinguished from PUB-supported adapters. Public metadata summaries inform generation without accessory names or readings.
- Settings → Hardware check opens a local test app through the same isolated runtime and permission broker as generated apps. No model call is needed.
- Native UI components: column, text, button, choices, input, scoped captured images, native vector/generated-PNG graphics (four photos/graphics combined per screen), and meter (for example a tuning meter). All are drawn in the app's style: the user's style guide, or PUB's default style for an app set not to follow it (see `docs/style-guide.md`). Each dispatch is bounded; the native process watchdog also covers interpreter stalls.
- `storage.project` permits at most 8 KiB of JSON state per app. Preview data is temporary until saved.
- `storage.files` gives an app a private file folder (`files/app-files/<app id>/`) that only it uses, through `files.request` effects the host validates and performs off the main thread: list, stat, read, write (atomic replace or append), mkdir, delete, move, copy and usage, at most 12,000 bytes per read or write. Limits: 256 MiB and 5,000 files and folders per app (photos count separately); relative ASCII names, 8 levels, 256 characters. A read-only `photos/` folder lists the app's camera photos, so an app finds them again in later sessions; deleting one there deletes the photo. No permission prompt is involved. The folder is not visible to other PUB apps, other Android apps or the Files app, is never uploaded or sent to ChatGPT (edits receive only the code) and is deleted with the app. A new app's preview files are temporary: Save locally moves them into the app, closing discards them and startup removes abandoned ones. An edit preview works on a copy of the app's files (it needs that much free space), so Save changes keeps the saved app's files untouched and discards the preview's changes. See `docs/files.md`. Host-generated UUIDs identify files; model-provided names never become paths. An app saved from the former built-in tuner (a development fixture current builds no longer ship) keeps its legacy ID `guitar-tuner` and all its data; no other app gets that ID.
- `files` (Settings → Access → Files on this phone) lets an app use documents and folders the user picks in Android's system file picker, with the user's permission: one or several files, a folder, or a new document the user names and places (Save as), in the phone's shared storage, Downloads or other apps that offer documents (such as Drive). PUB has no storage permission and cannot browse the phone; the app sees only what the user picks, by an opaque handle, name, size and type, never paths or content URIs, and never other apps' private data. It can read and write picked files, create, rename and delete inside a picked folder (deleting always from a tap), and import or export between them and its private folder. The picker always starts from a tap; with Ask, PUB's dialog asks once per session. Saved apps keep access (Android persistable permissions, released only when no saved app needs a document) until the app releases it, the user chooses **Forget file access** for that app in Settings → Access, or the app is deleted; at most 32 per app. Preview access ends when the preview closes and is not kept by Save locally; an edit preview can read, but not change, the saved app's picked files. Access revoked outside PUB is reported to the app. Documents are never deleted with an app. See `docs/files.md`.
- Every hardware group has global block/default and per-project rules enforced by the native host. New hardware access starts from a user action; native camera/device pickers cannot be opened by script callbacks. Switching apps, backgrounding, revocation and closing stop hardware sessions and invalidate queued results. Preview grants are session-only. Android permissions and explicit device selection remain additional requirements.
- Photos are private JPEG assets scoped to the host project identity: full captured resolution, remembered JPEG quality, maximum 20 photos / 1 GiB per project, 256 MiB each. Saving streams the JPEG without resizing or recompressing; only display previews are sampled. Personal metadata is removed, with orientation and color profiles retained. Previews are temporary; save copies their assets, close removes them, and startup removes abandoned temporary captures.
- ChatGPT tokens are encrypted using AES-GCM with a non-exportable Android Keystore key, atomically stored in the host's no-backup directory. Tokens never enter prompts, projects, script events, logs, or source control.
- Disconnect revokes the renewable session and clears local tokens. If remote revocation fails, PUB reports it and directs the user to ChatGPT Settings. Saved apps are retained.
- Content reports (Google Play's AI-Generated Content policy): **Report content** on a build result, **Report research** on the Research card and **Report app** in a launcher tile's long-press menu open an in-app form. It has a reason, optional details, and an **Include** option, checked by default, that attaches the app's name, description and code (up to 40,000 characters) or the research summary and sources. The report is sent to the developer's endpoint (`tools/report-endpoint`, a Google Apps Script web app that stores reports in a Google Sheet), never to OpenAI. It never contains phone context, account details, saved data, files or photos (`core/ContentReport`). Builds without an endpoint show that reporting isn't set up.
- Settings and Help & guide link to the privacy policy (`docs/privacy-policy.md` by default; see "Release builds").

## Build and test

Requirements: JDK 17, Android SDK 36/build-tools 36.0.0. PUB targets Android 16 (API 36), as Google Play requires for new apps and updates since August 31, 2026, with Android 12 (API 31) as the minimum. Gradle 8.11.1, AGP 8.10.1, Kotlin 2.1.20. On this prepared machine:

```powershell
.\tools\dev.ps1 :core:test :app:assembleDebug :app:lintDebug
.\tools\dev.ps1 :app:assembleDebugAndroidTest :app:installDebug
```

With your own Android toolchain, use `gradlew.bat` and set `JAVA_HOME`, `ANDROID_HOME`, and `local.properties`. The local `.toolchain` directory and credentials are ignored by Git.

APK: `app/build/outputs/apk/debug/app-debug.apk`.

Debug builds are unoptimized and debuggable, so they are not representative of performance. To check speed on a phone, build the R8-optimized `benchmark` variant (signed with the local debug key; never publish it): `.\tools\dev.ps1 :app:assembleBenchmark`, then install `app/build/outputs/apk/benchmark/app-benchmark.apk`. `release` is optimized the same way and is signed with your upload key (see "Release builds").

```powershell
.\.toolchain\android-sdk\platform-tools\adb.exe install -r app\build\outputs\apk\androidTest\debug\app-debug-androidTest.apk
.\.toolchain\android-sdk\platform-tools\adb.exe shell am instrument -w -r app.pub.test/androidx.test.runner.AndroidJUnitRunner
```

Unlock the phone and keep PUB foreground for microphone instrumentation. Default tests use synthetic local project fixtures; microphone tests save a tuner fixture app from the test APK (`app/src/androidTest/assets/fixtures/tuner`) and remove it afterwards. Explicitly opted-in live ChatGPT tests use the connected account and submit generation/review requests. The credential-storage test uses a separate test file. See `docs/chatgpt-builder.md` for the protocol and validation status; `docs/architecture.md` describes the original runtime proof.

## Release builds

Google Play needs a signed App Bundle (`.aab`). `bundleRelease` and `assembleRelease` refuse to run until they have an upload key and a report endpoint. This keeps an unsigned bundle, or one whose Report content form can't send, from ever reaching Play. The settings are Gradle properties or environment variables, and none of them belong in Git:

| Gradle property | Environment variable | Value |
|---|---|---|
| `pub.upload.storeFile` | `PUB_UPLOAD_STORE_FILE` | Path to your upload keystore, kept outside the repository (for example `C:/Users/you/keys/pub-upload.jks`) |
| `pub.upload.storePassword` | `PUB_UPLOAD_STORE_PASSWORD` | Keystore password |
| `pub.upload.keyAlias` | `PUB_UPLOAD_KEY_ALIAS` | Key alias. Defaults to `upload`. |
| `pub.upload.keyPassword` | `PUB_UPLOAD_KEY_PASSWORD` | Key password. Defaults to the keystore password, as keytool's PKCS12 keystores use. |
| `pub.reportEndpoint` | `PUB_REPORT_ENDPOINT` | The `https://…/exec` URL of your deployed report endpoint (`tools/report-endpoint/README.md`) |
| `pub.privacyPolicyUrl` | `PUB_PRIVACY_POLICY_URL` | Optional. Defaults to `https://github.com/zeniazenin/PUB/blob/main/docs/privacy-policy.md`, which works once that file is pushed. |

`tools\dev.ps1` uses `.toolchain\gradle-home` as Gradle's user home, so the simplest place for the properties is `.toolchain\gradle-home\gradle.properties`, which Git ignores. Write paths with forward slashes, because a properties file treats `\` as an escape character. Then:

```powershell
.\tools\dev.ps1 :core:test :app:lintRelease :app:bundleRelease
```

The bundle is `app\build\outputs\bundle\release\app-release.aab`. Create the upload key and publish the app as described in `docs/google-play-release.md`.

## Layout

- `core`: isolated JS engine, UI/package validation, style guide and colour schemes (`StyleGuide`, `StyleColors`), pitch detection, permission policy, OAuth/identity and response-stream validation.
- `app/auth`: ChatGPT OAuth, encrypted session storage, refresh, revocation, model catalog and Responses stream.
- `app/builder`: research, UI planning, icon design, generation prompt/contract, behavior checks and cancellable account/generation state.
- `app/projects`: atomic local package library, per-app specs (original request, research brief, behavior checks) and each app's private file folder (`AppFiles`).
- `app/runtime`: isolated service and bounded Binder protocol.
- `app/hardware`: capability broker, native adapters, camera/media storage, files on the phone (system picker, grants, document access) and Hardware check.
- `app/permissions`, `app/audio`, `app/ui`: native broker, microphone processing, Compose renderer, theme (`PubTheme`, type pairings, shapes), PUB's components and icons (`PubComponents`) and the style guide screen. `app/res/font`: the bundled fonts. See `docs/design-language.md`.
- `app/reports`, `app/ui/ReportDialog.kt`, `core/ContentReport`: the in-app content report form and its sender. `tools/report-endpoint`: the Apps Script endpoint that receives reports.
- `app/assets/samples/tip-calculator.json`: the sample app package. On first launch, a library without any saved app gets one copy as an ordinary app with a new ID (`app/projects/SampleApps.kt`); the host preference `samples.seeded` keeps it from being added again.

## Remaining limits

Generated apps are limited to PUB's component/effect contract, not arbitrary Android apps. Apps reach files outside their private folder only when the user picks them (no browsing, background access, sharing to other apps or online-only documents such as Google Docs); the system picker and real document providers have not yet been tested on a phone. Video, raw camera frames, OCR, private/health sensors, biometric templates, Wi-Fi configuration, arbitrary USB drivers, NFC writes/payments, proprietary accessory protocols, scheduled/background work inside generated apps, package sharing and general networking are not implemented. Builder generation/review can run in the background; submitted build drafts are checkpointed, but idle unsent prompt changes are not autosaved. Bluetooth audio routing does not implement Galaxy Buds noise-cancellation controls. Accessory compatibility requires its documented protocol; hardware absence returns an error. The user must test each generated app; a valid initial UI is not a correctness guarantee. A follow-up change that completes replaces the draft; there is no undo to an earlier version of a draft (describe the reversal as another change, or discard the draft). OAuth process-death recovery starts a fresh login; it never persists an unfinished authorization code/verifier. Pitch accuracy of microphone apps against a reference tuner remains a manual test.

## Launcher editing (0.4.3)

Long-press an icon, choose Edit app, and describe the changes (typing or voice). Generation receives the current app package as context; saved data/photos are not included. An edit also builds on the app's saved spec: research receives its saved brief and returns the complete updated brief, and generation receives its original request and behavior checks and returns the complete updated suite (see `docs/research.md` and `docs/behavior-checks.md`). Saving the edit keeps the original request and replaces the brief and checks with the edit build's. Preview uses temporary state initialized from existing saved data, a snapshot of the app's private files and read-only access to that app's existing photo assets. Camera captures, file and state changes made in preview are discarded. Save changes atomically updates the package under the same app ID, preserves original data/files/photos/permission rules, and refuses a stale update if the package changed or was deleted. Review requested capabilities before previewing. (Current builds no longer bundle the tuner; it was a development fixture. Apps saved from its editable override keep working as ordinary apps.)

Verification: 57 JVM tests and seven targeted on-phone tests pass. Device checks cover menu accessibility, edit context, delete cancellation/confirmation, preview isolation, same-ID updates, saved data/photos/permissions, launcher and builder regressions. No paid model-generation request was made during verification; tests exercise prompt assembly and use fixture output for the local edit/save flow. Build/lint pass with zero errors.

## Prompt history and graphics (0.5.0)

Launcher → Edit app → Prompt history shows construction history for that app. New unsaved drafts have their own session history, attached to the app on first save. The local store retains the latest 200 submitted requests with timestamp, model, app linkage and outcome. Records are atomic/private/local; earlier unrecorded requests cannot be recovered. Failed/cancelled/interrupted requests remain reviewable. App deletion keeps history; history does not contain generated code, device context, photographs or credentials and is not automatically included in generation.

Packages optionally contain `assets` (up to eight) and `icon` (an asset ID). The launcher icon is a pictogram (`AppIcon`: a 48-unit vector without text) that a separate, short build step (`IconDesigner`) designs from the app's name, description and research whenever a build has none; edits and repairs keep the existing one, and the build never fails for its icon. The host refines each design (half-unit coordinates, the icon palette, no invisible or repeated shapes), asks once more for a simpler one when it is too busy, and draws every pictogram in one theme tint as pixel art: fitted to the same size, rasterized onto a 24-cell grid with one-pixel outlines and drawn as LCD cells, with an optional soft duotone fill (`AppIconTile`), so icons share one minimalist retro style (the tile's corners follow the style guide; see `docs/design-language.md`); apps without an icon show a built-in pictogram or a neutral app symbol, never letters. Assets are strict native vectors or PNG-generation requests. Vector colours are fixed hex values or theme colour names (Material colour roles such as `primary`, `secondaryContainer` or `onSurfaceVariant`), which follow the style guide and its light or dark mode, also after the user changes it. Vector parts have unique IDs; UI graphic nodes can change their `highlight` list without changing the asset. Schematics should use vectors so individual strings/parts can react to state. A tuner app, for example, can highlight the nearest confident string by pitch and clear it on silence/stop. (Current builds no longer bundle the tuner that first showed this; it was a development fixture. Apps saved from it keep working.)

The builder invokes the Responses image-generation tool for up to two requested PNG assets through the existing ChatGPT OAuth connection. Images are stored with the local app, decoded at bounded preview sizes and reused on edits when ID/prompt match. Pixel data is omitted from edit prompts. Tool failures refuse the draft instead of silently replacing imagery with ASCII. Tool access is account/model-dependent; no API key is introduced.

Graphics never grant network, files, SVG/HTML execution or arbitrary Android access to JavaScript. The host draws only validated shapes and decodes bounded PNG data. Package storage is bounded to16MB, source remains64KiB, script UI packets remain32KiB. At most two generated PNGs, each4MiB and4MP/2048px per side, fit within a package.

## Follow-up changes

After a build the builder is on its Review step, which is about refining the draft. It shows the draft (with **Try it** pinned below) first, then a **Request changes** box: type what should change or tap **Speak a change** (the same speech service as **Speak your idea**; recognized text is added to the box and never builds on its own), then tap **Apply changes**. Each change builds on the current draft exactly like an edit builds on a saved app: research updates the draft's brief, the planner updates its UI plan, and the builder receives the draft's code, original request and behavior checks. When the change's draft is ready the box clears for the next one, and **What you asked for** lists the idea (or, when editing a saved app, the first change) and every change since; automatic repairs are not listed. If a change fails or is cancelled, the previous draft stays and the box keeps its text for a retry.

When the draft's behavior checks still fail or its latest visual review still asks for fixes, **Quick fixes** chips add those findings to the box as editable text. Nothing is sent until **Apply changes**, and nothing new leaves the phone: the text is what the builder already shows.

A builder preview has **Request changes** beside **Save locally** / **Save changes**: it closes the preview and returns to the box. A saved app that is open has **Edit** next to **✕**, which opens the builder for that app (unless the builder still holds another app's build result). The draft's requests are kept with the build draft (`files/builder-draft.json`, version 6), so they survive Android closing PUB. See `docs/follow-up-changes.md`.
